# 상세 페이지 만드는 사람에게

이 글을 끝까지 읽고 시작한다. `PARTS.md`(부품 목록)와 짝이다.

## 0. 네가 하는 일

프로젝트 하나의 원자료(발표 장표 · 보고서 · 피그마)를 읽어
**상세 페이지 본문 한 장**을 만든다. 파일 두 가지만 남기면 된다.

```
case-<프로젝트 id>.js      본문 마크업
images/<프로젝트 id>/       그 페이지가 쓰는 그림
```

이 둘 말고는 **아무 파일도 건드리지 않는다.**

## 1. 절대 하지 말 것

```
✗ 공유 파일 수정
    case.css · case.js · project-detail.js · tokens.css · system.css
    index.html · projects.html · about.html · project-detail.html
    다른 프로젝트의 case-*.js
✗ git 명령 (add · commit · push · checkout 무엇이든)
✗ 배포 · 판 번호(?v=) 손대기
✗ 디자인 값 정하기 — 글자 크기 · 색 · 여백을 style= 로 적지 않는다
✗ PARTS.md 에 없는 클래스 만들기
✗ 모르는 것 지어내기          ← 가장 중요하다. 아래 3번을 본다
✗ 주시원_포트폴리오_웹_화면설계서_v0.5.html 수정
```

막히면 멈추고 보고한다. 우회하지 않는다.

## 2. 먼저 읽을 것 — 순서대로

1. `tools/case/PARTS.md` — 쓸 수 있는 부품 전부
2. `case-korail.js` — 완성된 본보기. **이것이 기준이다**
3. `project-detail.js` 안 네 프로젝트의 `sections` — **이미 검수된 사실이다.**
   원자료와 어긋나면 이쪽을 믿고, 어긋났다는 사실을 보고한다
4. `index.html` 의 HOW I PLAY 절 — 네 프로젝트가 쓴 방법이 CHECK · MATE ·
   CHECKMATE 로 나뉘어 적혀 있다. **이것이 원자료에서 무엇을 찾을지의 목차다**
5. `images/case/` — 이미 쓰고 있는 그림. 같은 것을 또 뽑지 않는다

## 3. 사실을 다루는 법

```
수치를 쓸 때      반드시 원자료에서 읽은 값만. 어림잡지 않는다
                  마크업 주석에 어디서 왔는지 남긴다
                  예) <!-- 성공률 89% — 2차 사용성평가 13쪽 -->

모를 때          <span class="bk">[빈칸]</span> 으로 두고
                  보고서의 '못 찾은 것' 목록에 적는다

어긋날 때         project-detail.js 의 기존 원고를 믿는다
                  어긋난 내용을 보고한다
```

**원자료에 없는 문장을 그럴듯하게 지어내는 것이 이 작업에서 가장 큰 사고다.**
빈칸이 남은 페이지는 고칠 수 있지만, 틀린 사실이 올라간 페이지는 신뢰를 잃는다.

## 4. 글투

```
문장     ~했습니다 체가 아니라 ~했다 체.  (코레일톡 본문이 그렇다)
         개조식(~함 · ~임)은 쓰지 않는다
주어     '저' 를 쓰지 않는다. 팀이 한 일은 팀 주어로, 내가 한 일은 주어 없이
이름     팀 명단 외에 다른 팀원 이름을 본문에 쓰지 않는다
길이     bl 본문은 한 문단 두세 줄. 길면 타일이나 목록으로 쪼갠다
강조     <b> 만 쓴다. 색이나 밑줄로 강조하지 않는다
숫자     천 단위 쉼표. 범위는 ~ 가 아니라 — (예: 2026.03 — 07)
가운뎃점  항목을 잇는 점은 ` · ` (앞뒤 한 칸)
```

## 5. 절을 짜는 법

1. HOW I PLAY 에 적힌 그 프로젝트의 방법 목록을 꺼낸다
2. 각 방법이 원자료 **몇 쪽**에 있는지 찾는다
3. 가까운 것끼리 묶어 절 4~7개를 만든다
4. 절 이름은 **그 프로젝트가 실제로 지나온 단계**로 짓는다.
   코레일톡의 절 이름(문제정의 · 개선안 설계 …)을 억지로 가져다 쓰지 않는다
5. 절마다 블록 1~3개. 블록마다 부품 하나

한 절의 모양은 늘 같다.

```
절 머리 (번호 · 이름 · 쓴 방법 칩)
  블록
    꼬리표 → 제목 → 본문 → [타일 격자 | 갤러리 | 경로 | 표 | 막대 | 도넛]
```

### 균형 맞추기

```
갤러리    한 절에 하나. 한 묶음 5~15장
타일      한 격자에 최대 6칸
표        가로 6칸까지
절        4~7개. 절마다 블록 1~3개
```

한 절이 갤러리 하나로만 끝나면 안 된다 — 앞에 제목과 본문이 꼭 있어야 한다.

## 6. 그림 뽑는 법

```
어디에     images/<프로젝트 id>/ 아래. 묶음별로 폴더를 나눠도 된다
무엇을     원본이 그림인 것만 — 아이트래킹 시선 그림 · 프로토타입 화면 ·
           사진 · 복잡해서 다시 그릴 수 없는 도표
무엇을 안   수치 · 표 · 타일로 옮길 수 있는 것은 그림으로 넣지 말고 마크업으로 짠다
           (PARTS.md 의 7 · 8 · 11번)
형식       webp. 긴 변 2880px 이하. 장당 200KB 를 넘기지 않는다
이름       뜻이 드러나게. ut1_01.webp · proto_03.webp 처럼
```

장표를 통째로 그림으로 넣는 것은 **마지막 수단**이다.
그 장표의 수치와 표를 마크업으로 옮길 수 있는지 먼저 본다.

## 7. 다 만들면 확인할 것

```
1  node --check case-<id>.js                          문법
2  태그 열림/닫힘 수가 맞는지                            div · section · button
3  PARTS.md 에 없는 클래스를 쓰지 않았는지
4  images/<id>/ 의 모든 그림이 마크업에서 쓰이는지
5  마크업의 모든 src 가 실제로 있는 파일인지
```

## 8. 보고 형식

마지막 답으로 아래를 낸다. 짧게.

```
만든 것     case-<id>.js  (몇 줄 · 절 몇 개)
            images/<id>/  (몇 장 · 합계 몇 MB)

절 구성     01 이름 — 쓴 부품 (타일 4 · 갤러리 8장)
            02 이름 — …

쓴 수치     값 — 출처 (파일 · 쪽)
            값 — 출처

못 찾은 것   무엇이 없어서 [빈칸] 으로 두었는지

어긋난 것   기존 원고와 원자료가 다른 지점
```
